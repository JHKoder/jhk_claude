- 커밋 메시지는 간결하게 작성한다
- 커밋 제목은 영어, 본문은 한국어로 작성한다
- 본문은 코드리뷰자 입장에서 읽기 쉽게 작성한다.
- git-flow 브랜치 전략을 따른다 (아래 표 참조)
- 커밋 기록에 클로드는 남기지 않는다
- Co-Authored-By에 클로브 표시 금지
- main,dev,develop 브랜치일때 커밋하지 않는다.
- 기능적 응집도를 기준으로 [기능 구현], [성능/인프라], [테스트] 단위로 변경 사항을 엄격히 분리하여 커밋할 것.
- 코드 리뷰의 효율성을 위해 각 커밋은 서로 다른 관심사를 침범하지 않는 최소 단위로 구성할 것.

| 브랜치        | 용도                               |
|------------|----------------------------------|
| `main`     | 라이브 서버 출시 브랜치                    |
| `release`  | 배포용 브랜치                          |
| `hotfix/*` | main 브랜치 긴급 버그 수정                |
| `develop`  | 다음 출시 버전 통합 브랜치 (develop → main) |
| `feat/*`   | 기능 개발 브랜치 (feature → develop)    |


### 브랜치 명명 규칙

`유형/설명` 형식

```
feat/ticket-reservation
feat/chat-realtime
hotfix/seat-double-booking
```

## 1. 커밋 메시지 컨벤션

형식: `[커밋 유형]: [커밋 제목]`

### 커밋 유형

| 유형                 | 의미                            |
|--------------------|-------------------------------|
| `feat`             | 새로운 기능 추가                     |
| `fix`              | 버그 수정                         |
| `refactor`         | 코드 리팩토링 (동작 변화 없음)            |
| `test`             | 테스트 코드 추가 및 리팩토링              |
| `perf`             | 성능 개선                         |
| `docs`             | 문서 수정                         |
| `chore`            | 패키지 매니저 수정, 기타 (.gitignore 등) |
| `style`            | 코드 포매팅, 세미콜론 누락 등 코드 변경 없는 경우 |
| `design`           | CSS 등 UI 디자인 변경               |
| `comment`          | 필요한 주석 추가 및 변경                |
| `rename`           | 파일·폴더 이름 변경 또는 이동             |
| `remove`           | 파일 삭제                         |
| `!BREAKING CHANGE` | 커다란 API 변경                    |
| `!HOTFIX`          | 치명적인 버그 긴급 수정                 |
